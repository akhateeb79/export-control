- Each parameter stores: eccn_code, parameter_name, threshold_value,

- Category must be queryable (0-9)
- Product group must be queryable (A-E)
- Parameter thresholds must be comparable numerically
- Seed with real CCL structure — at minimum categories 0-9 with

Add a control_list_versions table if not already present:

BUILD PART 2 — Three-Stage Classification Pipeline

STAGE 1 — Attribute Extraction (cheap model)
- Model: use claude-haiku-4-5 (cheapest, fastest)
- Prompt: loaded from agent_versions table where agent_type = 'CLASSIFIER_EXTRACTION'
  and status = 'PUBLISHED' — never from source code
- Input: product name, technical description, specifications from the case
- Output must be structured JSON:
  {
    "category": "0-9 or null",
    "product_group": "A-E or null", 
    "key_parameters": {"param_name": "value"},
    "country_of_origin": "ISO code or null",
    "confidence": 0.0-1.0,
    "insufficient_fields": ["list of missing parameters if any"]
  }
- If category cannot be determined with confidence: return null for category
  A wrong category permanently removes the correct ECCN from consideration
  Null is the correct answer when uncertain — never guess
- If critical parameters are missing: return INSUFFICIENT_INFORMATION 
  with the parameter names listed

STAGE 2 — SQL Candidate Filtering (no model call)
- Use Stage 1 attributes to filter eccn_entries
- Filter by category if not null
- Filter by product_group if not null  
- Match parameter thresholds numerically where provided
- Return 5-10 candidates maximum
- If zero candidates survive: immediately route to human classification
  Set classification status = NEEDS_HUMAN_REVIEW
  Never call Stage 3 with an empty or guessed candidate set
- If category is null from Stage 1: broaden the filter, return top 10 
  by text similarity, flag confidence as LOW

STAGE 3 — Reasoning (capable model)
- Model: use claude-sonnet-4-6
- Prompt: loaded from agent_versions table where agent_type = 'CLASSIFIER_REASONING'
  and status = 'PUBLISHED' — never from source code
- Input: full text of the 5-10 candidates ONLY, plus the original 
  product description — never the full CCL
- Output must be structured JSON:
  {
    "eccn": "code or EAR99 or null",
    "confidence": 0.0-1.0,
    "reasoning": "detailed explanation referencing specific parameters",
    "cited_entry": "the specific CCL entry relied upon",
    "rejected_candidates": [
      {"eccn": "code", "reason": "why rejected"}
    ],
    "us_content_percentage": null or 0-100,
    "de_minimis_status": "SUBJECT | NOT_SUBJECT | UNKNOWN",
    "requires_human_review": true or false
  }
- If confidence is below the tenant threshold: flag for human classifier
  Do not block the case — route to NEEDS_HUMAN_REVIEW

STORE RESULTS in classification_results:
- eccn_code, confidence, reasoning, cited_entry, agent_version_id, 
  control_list_version_id, status, requires_human_review
- agent_version_id: the exact agent_versions row used — never null
- control_list_version_id: the ACTIVE version at time of classification

CACHE LOGIC:
- On case submission: check tenant product catalogue for existing 
  classification of the same product
- If found AND control_list_version_id matches current ACTIVE version:
  return cached result immediately, no agent call
- If found AND control_list_version_id does NOT match current ACTIVE:
  flag as requires_revalidation = true, run classification again
- If not found: run the three-stage pipeline, store result in catalogue

CACHE INVALIDATION:
- When a new control list version becomes ACTIVE:
  UPDATE all classification_results 
  SET requires_revalidation = true
  WHERE control_list_version_id != new_active_version_id
  This must run inside the same transaction that activates the new version
